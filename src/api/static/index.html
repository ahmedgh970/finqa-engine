Résultats mesurés

150 questions d'analystes de FinanceBench sur 368 rapports SEC, tout en local sur un GPU de 8 Go. Chaque étage du workflow est là parce qu'une mesure l'a justifié, et chaque mesure ne change qu'une chose à la fois.

L'échelle du workflow, à 12K tokens de contexte

Bonnes réponses sur 150 : correctes, avec la page de preuve dans le contexte. Mêmes 20 passages pour chaque ligne, même modèle (granite4.1:8b), même juge.

La recherche

Part des pages de preuve retrouvées dans les 10 premiers passages (recall@10, chunks de 512 tokens).

  • Densetoute la collection 0.30
  • Densefiltrée sur le rapport 0.55
  • + Rerankerretenu, ADR 0001 0.65

BM25 et la fusion hybride ont été essayés et écartés : le reranker apporte le gain le plus fort.

Sur le run de référence, 11 calculs sur 11 sont justes et les 120 questions non routées gardent une réponse identique. Le gain net est d'une bonne réponse, dans le bruit : l'apport, c'est un chiffre vérifié par le code, avec ses lignes sources. En démo avec qwen3.5:4b, un faux accepté a été trouvé (le chiffre d'affaires 2019 pour une formule « FY2020 revenue ») : il a donné une règle de plus, sans aucune régression sur les 90 extractions rejouées.

Comment c'est mesuré

  • Une grille à cinq issues sépare « le modèle s'est trompé » de « la preuve n'était pas dans le contexte » : elle dit quel étage corriger.
  • Le juge local (qwen3.5:9b) a été validé contre une référence sur des runs qui n'ont pas servi à le régler (kappa 0.81).
  • La recherche est rejouée à l'identique : deux lignes ne diffèrent que par l'étage testé.
  • Modèles open-weight en 4 bits (Q4_K_M), latences mesurées sur un GPU laptop de 8 Go ; chaque décision est consignée dans une ADR.
