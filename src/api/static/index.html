Pourquoi ce découpage

  • Chaque brique se dimensionne seule : plus d'utilisateurs, on ajoute des réplicas d'API ; plus de génération, des GPU vLLM.
  • L'API reste sans GPU et sans état : elle se déploie et se remplace comme n'importe quel service web.
  • Remplacer une brique ne touche pas les autres : un autre modèle, c'est une ligne de config ; un autre embedder, une réindexation.
  • La qualité est surveillée comme la latence : la CI rejoue le golden set et bloque un changement qui fait baisser les bonnes réponses.
  • Les données ne sortent pas : modèles open-weight auto-hébergés, chaque réponse cite ses sources.

Résultats mesurés

150 questions d'analystes de FinanceBench sur 368 rapports SEC, tout en local sur un GPU de 8 Go. Chaque étage du workflow est là parce qu'une mesure l'a justifié, et chaque mesure ne change qu'une chose à la fois.

Sur le run de référence, 11 calculs sur 11 sont justes et les 120 questions non routées gardent une réponse identique. Le gain net est d'une bonne réponse, dans le bruit : l'apport, c'est un chiffre vérifié par le code, avec ses lignes sources. Lors d'un test avec qwen3.5:4b, un faux accepté a été trouvé (le chiffre d'affaires 2019 pour une formule « FY2020 revenue ») : il a donné une règle de plus, sans aucune régression sur les 90 extractions rejouées.

Comment c'est mesuré

  • Une grille à cinq issues sépare « le modèle s'est trompé » de « la preuve n'était pas dans le contexte » : elle dit quel étage corriger.
  • Le juge local (qwen3.5:9b) a été validé contre une référence sur des runs qui n'ont pas servi à le régler (kappa 0.81).
  • La recherche est rejouée à l'identique : deux lignes ne diffèrent que par l'étage testé.
  • Modèles open-weight en 4 bits (Q4_K_M), latences mesurées sur un GPU de 8 Go ; chaque décision est consignée dans une ADR.
